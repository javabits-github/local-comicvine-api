### 2026-11-16 — Server flow diagram: removed the spurious second DB visit (DOC-2)

- **Context:** while reviewing the [docs/architecture.md](docs/architecture.md) server request-flow diagram, the list/detail branch appeared to have two arrows into `localcv.db` — one from `buildResourceConfig` and one from `resolveLimit`. The source had exactly one `CFG --> Q` edge, so the perceived "double arrow" was the renderer routing the backward `L --> Q` edge (a `flowchart TB` cycle artifact: `Q` is visited at two ranks). But rendering it in a browser and tracing the code showed a genuine defect: the branch ran `buildResourceConfig → Q → parseFilters → parseSort → resolveLimit → Q → buildResult`, i.e. the database was drawn being queried **twice**.
- **Change:** the list handler ([src/server.js](src/server.js)) resolves `limit` → `filters` → `sort` and then runs the DB **once** (`COUNT(*)` + `SELECT`), so `buildResourceConfig` never data-queries before the parameters are parsed (it only runs `PRAGMA table_info` schema checks via `tableColumns`). The diagram now reads `buildResourceConfig → parseFilters → parseSort → resolveLimit → localcv.db → buildResult` (the `CFG --> Q` / `Q --> F` pair became a single `CFG --> F`). The search branch's `loop selected resources ↔ localcv.db` cycle is correct (one query per selected resource) and is unchanged. Render-verified in a browser (mermaid v11): the `Q` node now has one incoming edge per branch.
- **Gotcha / follow-up:** the parameter-parsing order in the diagram (`parseFilters → parseSort → resolveLimit`) follows the README/skill description; the code actually calls `resolveLimit` first, then `parseFilters`, then `parseSort`. The order among the three is immaterial to the diagram (none touches the DB) and was left as-is to match the documented flow.

### 2026-11-16 — Publisher blocklist → allowlist (SRV-34)

- **Context:** SRV-12 added a publisher **blocklist** (`COMICVINE_PUBLISHER_BLOCKLIST` / the `publisherBlocklist` option, a `publisher_id NOT IN (...)` predicate) that excludes a publisher's volumes from volume search and list. The motivating use case is better served by the inverse: include **only** the listed publishers' volumes.
- **Change:** [src/server.js](src/server.js): the predicate is now `publisherAllowlistPredicate` — `publisher_id IN (...)` — driven by `COMICVINE_PUBLISHER_ALLOWLIST` (comma-separated) or the `publisherAllowlist` option (array of ids); "allowlist" naming follows SRV-14's CORS convention. **Key semantic decision:** an empty/absent allowlist means **no restriction** (a no-op until populated) rather than "nothing allowed" — the naive whitelist footgun (every volume disappears) is avoided, so existing deployments are unchanged. The list-endpoint bypass is kept: an explicit `?filter=publisher_id=`/`publisher=` term skips the allowlist for that request; on search (no `?filter`) it always applies when set. `parseIdList` still ignores non-numeric tokens. Updated the README "Publisher allowlist" section, [.env.example](.env.example), and the api-contract instructions; the SRV-12 test became two SRV-34 tests in [test/server.test.js](test/server.test.js) (allowlist restricts search + list with the explicit-filter bypass; empty allowlist = no-op). Full suite 136 = 134 pass + 0 fail + 2 skip.
- **Gotcha / follow-up:** the rename is a breaking change for anyone who had set `COMICVINE_PUBLISHER_BLOCKLIST` or passed `publisherBlocklist` — the old names are gone (no deprecation alias), so a deployment using the blocklist must switch to `COMICVINE_PUBLISHER_ALLOWLIST` with the **inverse** list (the publishers to keep, not the ones to drop).

### 2026-11-15 — FTS search gate counts the base table, not the index (SRV-32)

- **Context:** the SRV-5 FTS search gate in `buildResourceConfig` ([src/server.js](src/server.js)) decided whether to use the FTS5 trigram index via `SELECT COUNT(*) FROM <table>_fts > 0`, with the comment "the FTS table is external-content, so its row count tracks the base table only after a rebuild — gate on > 0 so an empty index does not silently match nothing." But for an **external-content** FTS5 table a bare `COUNT(*)` on the virtual table reads the *external content* (the base table), not the index. Verified 2026-11-14: after `INSERT INTO <fts>(<fts>) VALUES('delete-all')` (index fully emptied) the `COUNT(*)` still returns the base table's row count, while a `MATCH` against the emptied index returns 0 rows. So the gate passed whenever the base table had rows, regardless of index state — the exact "empty index silently matches nothing" case the comment feared. Reachable when a sync is interrupted after populating a base table but before `rebuildFtsIndex` runs, and the server then (re)starts: the gate flips to FTS and search returns nothing until the next sync rebuilds the index. Affects all eleven resources equally (pre-existing, not object-specific).
- **Change:** option (a) — gate on the FTS5 `_data` shadow table instead of the virtual table: `SELECT COUNT(*) FROM <table>_fts_data > 2`. The `_data` shadow table's rows track the index itself (unlike the external-content virtual table, whose `COUNT(*)` reads the base content). Verified 2026-11-15 against a scratch DB: the `_data` table has exactly **2 structural rows when empty** (fresh, or after `delete-all`) and more once populated (1 doc → 3, 50 docs → 4), so `> 2` means "populated". The `_idx` and `_docsize` shadow tables also track the index (0 when empty) but `_data` was the chosen discriminator. The existing `try`/`catch` is kept, so a missing `_data` table or any query error still falls back to LIKE. No updater or migration change — the `_data` shadow table is created automatically with the FTS5 virtual table, so it exists wherever the index does. New test: "search falls back to LIKE when the FTS index is empty (SRV-32)" — populates the base table, rebuilds the index, then `delete-all` to empty it (the interrupted-sync state: base has rows, index does not), and asserts search still returns the matching rows via the LIKE fallback. Full suite 135 = 133 pass + 0 fail + 2 skip.
- **Gotcha / follow-up:** the `> 2` threshold relies on an FTS5 internal (the empty-index structural row count is 2). It is stable across the SQLite versions in use, and the failure mode is benign — if a future SQLite changed the empty count, the gate would degrade to the old behavior (always-LIKE or always-FTS), not a correctness bug. The test is a genuine regression test: with the old gate it fails `0 !== 1` (the empty index is used and matches nothing); with the fix it passes (LIKE fallback returns the matches). The alternative option (b) — having the updater's `rebuildFtsIndex` write a "populated" marker the server gates on — was rejected as touching the updater + a migration for what a shadow-table read handles.

### 2026-11-15 — Person `death` double-encoding → nested object (SRV-33)

- **Context:** discovered during SRV-6d. `cv_person.death` is stored as a JSON string (the updater's `jsonify` serializes the live API's `{date, timezone, timezone_type}` object), but the person branch of `buildResult` read it via the plain scalar loop (`result.death = row.death`), so the server emitted it as a **string** rather than the nested object the live API returns. 2,234 of 90,168 persons have a non-null `death`. Verified against both DBs: `localcv.db` stores the keys as `{date, timezone_type, timezone}` (the order the updater saw), while the January raw dump (the verbatim live snapshot) has them as `{date, timezone, timezone_type}` — so a bare parse would keep the wrong key order. This is an accepted behavior change (string→object), so it was deferred out of SRV-6d (which must stay byte-for-byte) and done here as a dedicated output-correctness pass.
- **Change:** [src/server.js](src/server.js): a new `parseDeath` helper (next to `parseCredits`/`parseJsonColumn`) parses the stored JSON-text column and rebuilds the object in the live API's key order `{date, timezone, timezone_type}`, keeping only the keys that are present (any unexpected keys preserved after the known three); SQL `NULL` (a living person) and unparseable/non-object values become `null`. The person branch of `buildResult` special-cases `death` inside its scalar loop (`field === "death" ? parseDeath(row[field]) : row[field]`) so the key stays in its existing position (between `date_last_updated` and `email`) and the response key order is unchanged. No updater change (`jsonify(person.death)` already stores the object as a JSON string), no fieldConfig change (`death` is already in the person allowlist), and `sortablePersonFields` is untouched. New test in [test/server.test.js](test/server.test.js) (isolated DB + server): a person whose `death` is stored in the localcv.db key order is emitted as the reordered object (asserting both the value via `deepEqual` and the key order via `Object.keys`, since `deepEqual` ignores order), a living person stays `null`, and the list endpoint emits the same parsed object.
- **Gotcha / follow-up:** verified against the January raw dump (no live API key available): served `localcv.db` and fetched all 2,234 non-null deaths — every one is emitted as an object (0 strings), all in the live key order, and 2,085/2,091 match the dump's `raw_api_response.death` exactly; the 6 differences are pure `date`-value drift (the two DBs are snapshots from different times — `timezone`, `timezone_type`, and key order all matched). Full suite 133 = 131 pass + 0 fail + 2 skip.

### 2026-11-15 — Issue collections → `cv_issue_credit`/`cv_issue_image` join + presence bitmask (SRV-6f)

- **Context:** the issue pass of SRV-6 — the largest and last. `cv_issue`'s sixteen JSON collection columns: the seven credits (`character`/`person`/`team`/`location`/`story_arc`/`object`/`concept`), `associated_images`, `character_died_in`, `team_disbanded_in`, and the six `first_appearance_*`. Issues are the only resource whose collections the live API returns, so this is the core data. Verified against the verbatim raw-API dump (5,000 + 50,000 samples): the seven credits are `{id, name, api_detail_url, site_detail_url}` **except `person_credits`, which carries a `role`** (always present — 268,750/268,750); `associated_images` is `{id, caption, image_tags, original_url}` with `image_tags` always a **string**; the six `first_appearance_*` are **always null** in the dump. In `localcv.db` (1,138,624 issues) the six never-null collections (character/person/team/location/story_arc credits + `associated_images`) have null=0, while the ten nullable ones (object, concept, `character_died_in`, `team_disbanded_in`, the six `first_appearance_*`) have **17,986 NULL** (the UPD-7 window) and the six `first_appearance_*` additionally have **1,120,638 `"[]"`** rows (the Python-updater `|| []` coercion, F9.3). That settles the design: the **SRV-6c volume pattern** — a `credits_presence` bitmask distinguishes `[]` from null for the ten nullable collections; the six never-null emit `[]` when they have no rows.
- **Change:** [src/migrate.js](src/migrate.js): `cv_issue_credit` (`issue_id`, `credit_type`, `position`, `credit_id`, `name`, `role`, `api_detail_url`, `site_detail_url`; PK `(issue_id, credit_type, position)`, index `(credit_type, credit_id)`) and `cv_issue_image` (`issue_id`, `position`, `image_id`, `caption`, `image_tags`, `original_url`; PK `(issue_id, position)`) in `ensureJoinTables`, plus a **v12** migration that adds `cv_issue.credits_presence` (a 10-bit mask — bit i = the i-th nullable collection was a non-null array, in the fixed order object/concept/`character_died_in`/`team_disbanded_in`/the six `first_appearance_*`), backfills both join tables + the mask from the JSON columns (id-ordered batches of 2,000, DELETE-then-INSERT per (issue, type) so a re-run is idempotent), and drops the sixteen columns in one transaction (a no-op where already gone or the table is absent — `cv_issue` is Python-updater heritage, never created by `migrate()`, so a fresh database has no `cv_issue` and v12 is a no-op there). [src/updater.js](src/updater.js): `upsertIssue` is now a **schema-aware dispatcher** (an improvement over the other SRV-6 resources, which are final-schema-only) — `issueUsesJoinTables()` checks the `cv_issue` columns (the `character_credits` column's absence = final schema); the legacy JSON path (`upsertIssueJson`) is the exact pre-SRV-6f behavior, and the final path (`upsertIssueJoin`) writes the join rows + bitmask **live** (the issue detail call returns the collections on every sync) in one transaction. `syncIssues` computes the route once and passes it to every upsert. This keeps a partially-migrated database byte-for-byte and stops the next migration re-run from wiping join rows re-backfilled from NULLed columns; re-syncing clears the six `first_appearance_*` bits (live null), fixing the 1,120,638 `"[]"` artifacts (F9.3) that the migration preserves for byte-for-byte parity. [src/server.js](src/server.js): `ISSUE_CREDIT_TYPES`/`ISSUE_CREDIT_FIELDS`/`ISSUE_NULLABLE_CREDIT_TYPES` + `issueCreditRowToObject` (the `role` key only for person) + `issueImageRowToObject` + `buildIssueResult` (mask-driven for the ten nullable, `[]` for the six never-null + `associated_images`); the dispatch in the issue branch takes the join path only when `character_credits` is absent and both join tables exist (safer than a `credits_presence` check — a partial-failure window keeps the JSON path serving the original data), so `buildResult`'s issue branch (unchanged) remains the fallback. [src/fieldConfig.js](src/fieldConfig.js) needed no change (all sixteen already covered). New tests: a v12 migration test (3 rows → masks 15/0/1023 + idempotent re-run), an issue join-fixture server test (mask 1 and 0, person role, `associated_images`, never-null `[]`), updated migrate version assertions (11→12) + the join-table list, and the updater sync assertion (columns dropped, char/person join rows, person role, `credits_presence` 15). Full suite 132 = 130 pass + 0 fail + 2 skip.
- **Gotcha / follow-up:** verified against `localcv.db` (1,138,624 issues) on a subset copy (the full 1.1M-issue v12 backfill is too slow to run in a verification window, but it processes each issue independently, so a subset is faithful): a stratified 62-issue sample (the 17,986 NULL window, every populated collection, and the all-`[]` artifact) is **62/62 byte-identical** pre/post, and all sixteen collections are NULL or JSON arrays (no non-array divergence risk — a non-array non-null value would set the mask bit → `[]` while `parseCredits` → null). ### 2026-11-14 — Sync-window fallback baselines on the data instead of an arbitrary window (UPD-18)

- **Context:** when an endpoint has no `cv_sync_metadata.last_sync_date` (a first sync on a database that predates it, or a lost/corrupted row), the updater's `calculateSafeStartDate` fell back to **today − 30 days** (inherited from the Python updater in the UPD-3 rewrite) and `rawapi.js` fell back to the **snapshot date** (2026-01-22). Both are guesses: the 30-day window silently misses every entity updated before it, and the snapshot date assumes the database was built from the January snapshot — a database built from a newer snapshot (or an empty one) misses everything updated before the snapshot date.
- **Change:** both scripts now use a tiered fallback that can't miss rows. (1) A valid `last_sync_date` → one day before it, as before. (2) No usable `last_sync_date` but the table has rows → the newest stored `date_last_updated`, minus one day: a completed sync means everything newer than the newest stored row is exactly what is missing, so the window fetches precisely that (a stale database with a lost metadata row gets a window covering its actual staleness instead of a useless 30 days). (3) No usable `last_sync_date` and the table is empty → a **full sync** for that endpoint (no date filter), announced in the log — no window can populate an empty table. The updater adds a fourth tier: a table that does not exist at all (a fresh database — the four legacy tables are Python-updater heritage and are not created by `migrate.js`) is **skipped** with an error, since a full sync would only burn API calls into "no such table" failures (the tables arrive with DB-3's CREATEs, after which tier 3 applies). Two supporting details: the two-phase syncs' "ensure metadata row" INSERT is skipped for a full sync (`last_sync_date` is NOT NULL and a full sync has no window start to store — the row is created on the first resume-state save instead), and their resume state now carries a `full` flag so an interrupted full sync re-runs the full sync on the next run instead of mistaking the seeded `last_sync_date` for a real window.
- **Gotcha / follow-up:** verified against a copy of `localcv.db` with all metadata rows deleted: every endpoint baselines on its newest stored row (e.g. publishers → 2026-11-07 from a 2026-11-08 max), and the empty `cv_power` table correctly triggers a full sync. The auto full sync is deliberately **not** gated behind the `--full` confirmation: an empty table needs a full sync to get any data, the Docker cron runs unattended (a prompt would hang it), and the log announcement + Ctrl-C are the safety net. New tests cover all tiers in both scripts (full suite 118 = 116 pass + 2 skip).

### 2026-11-10 — Auto-recover missing volumes during issue sync (UPD-4)
 
- **Context:** the FK diagnostics from UPD-6 surfaced the *root cause* of the issue-sync FK failures: the local `localcv.db` is a synced subset, and an issue's `volume_id` can reference a `cv_volume` row that has no local row (e.g. a volume whose update window the volume sync didn't cover, or a volume that never made the subset). With `PRAGMA foreign_keys=ON`, the issue upsert threw `FOREIGN KEY constraint failed` and the whole issue endpoint aborted.
- **Change:** [src/updater.js](src/updater.js) now recovers these on the fly instead of aborting. The volume upsert is extracted into `upsertVolume(vol)` (used by `syncVolumes` and the recovery path) and the issue upsert into `upsertIssue(issueId, issueData, volumeId)`. In `syncIssues`, when an issue upsert throws an `FOREIGN KEY` error, the updater checks whether the issue's referenced `volume_id` has a local `cv_volume` row; if it is missing, it queries the live ComicVine API for that specific volume (`volume/4000-${id}/`), upserts it via `upsertVolume`, and retries the issue upsert once. If the volume cannot be fetched (rate-limit exhaustion or a bad reference), the issue is skipped gracefully — no stats increment, no resume-state advance, no metadata advance — rather than aborting the whole issue sync.
- **Gotcha / follow-up:** the recovery is best-effort per-issue; a volume that is genuinely absent from the live API (or rate-limited) leaves its issue skipped for that run, and `cv_sync_metadata` for issues is not advanced past the failure, so the next run re-attempts from the old safe start date. This closes UPD-4. Verified with two new tests in [test/updater.test.js](test/updater.test.js) against a temp FK-enabled DB: (1) a missing volume is fetched + upserted and the issue retry succeeds; (2) an unfetchable volume is skipped without aborting. Full suite: 60/60 green.
 
### 2026-11-10 — Diagnose FK failures during issue sync (UPD-6)

- **Context:** an `npm run sync` run was failing mid-issue-sync with `FOREIGN KEY constraint failed` and the endpoint's catch logged only "Skipping metadata update for issues" — no way to tell which FK, row, or SQL was at fault. The local `localcv.db` is a synced subset, so ~905 issues reference `cv_volume` rows that have no local row (`cv_issue.volume_id → cv_volume.id` is the FK that fires).
- **Change:** the pre-existing `runWithFkDiagnostics` helper in [src/updater.js](src/updater.js) was broken in two ways and is now fixed. (1) It iterated a `fk` variable that was never assigned — the `PRAGMA foreign_key_list(table)` query was missing — so it would have thrown `ReferenceError: fk is not defined` on any real FK failure. (2) In `syncIssues`, the upsert SQL was passed to an orphaned `this.conn.prepare(...)` call with no `.run()` and no assignment, so `runWithFkDiagnostics("cv_issue", issueSql, ...)` referenced an undeclared `issueSql` and **every** issue upsert threw `ReferenceError` before touching the FK. The helper now: queries `PRAGMA foreign_key_list(table)` (guarded by try/catch, degrading to SQL/params-only if the table has no FKs or doesn't exist), maps each FK column to its `?` position in the upsert's column list to resolve the offending value, checks whether the referenced row exists locally (`SELECT id, name FROM <ref_table> WHERE id = ?`, with a fallback to `SELECT id` only if the table lacks a `name` column), logs the FK definition + value + presence, and records a `sync_errors` row before rethrowing. The issue upsert SQL is now a real `const issueSql` template.
- **Gotcha / follow-up:** the diagnostics are a *symptom* fix, not a *root-cause* fix — the dangling issue→volume references still exist and the FK failure still aborts the issue endpoint (so `cv_sync_metadata` for issues is not advanced and the next run re-syncs from the old safe start date). The root-cause remediation (validate the issue's volume ref and skip/null when the volume is absent) is tracked as UPD-4. The `sync_errors` table is created via `CREATE TABLE IF NOT EXISTS` in the updater's schema setup, so the diagnostic insert works on fresh DBs too. Verified with a temp-DB repro: a bad issue (volume 999, missing) logs `FK: cv_issue.volume_id -> cv_volume.id; value=999; referenced row MISSING locally` and a `sync_errors` row, while a valid issue (volume 100, present) upserts normally.

### 2026-11-03 — Log the SQL behind a response (SRV-17)

- **Context:** the per-request log line records `method`, `path`, `query`, `status`, and `duration_ms` but not the SQL actually executed, so slow or misbehaving queries can't be inspected without re-implementing the handler's SQL by hand.

### 2026-11-03 — Log the response body (SRV-16)

- **Context:** the per-request log line records `method`, `path`, `query`, `status`, and `duration_ms` but not the response body, so a client can't tell *what* a request returned without replaying it.

The `write`/`end` wrapping is done once per request (not per call), so the overhead when enabled is a couple of `Buffer.concat` copies. See `TODO.md` SRV-16.

### 2026-11-02 — Multi-id filter on list endpoints (SRV-15)

- **Context:** a client wanted to fetch several volumes in one request with `?filter=id:59366|85128|…`. ### 2026-11-01 — CORS support (SRV-14)

- **Context:** the server set no CORS headers, so a browser client on a different origin was blocked by the same-origin policy — the live ComicVine API answers browsers, so the local mirror should too.
- **Change:** added configurable CORS in [src/server.js](src/server.js). The request handler computes the headers once per request (`corsHeaders`) and stashes them on the response so every `sendJson`/`sendFormattedResponse` path (JSON, XML, and JSONP) merges them in. `COMICVINE_CORS_ORIGINS` (comma/whitespace-separated) or the `corsOrigins` option is the allowlist. ### 2026-11-01 — Optional file logging with rotation (SRV-7)

- **Context:** every request/validation log went to stdout only, so long-running servers could not retain logs across restarts. SRV-7 asked for optional file logging with rotation, keeping stdout available.

- **Context:** `cv_volume_issue_ref` (from the SRV-6c backfill) stored the issue id *plus* a denormalized snapshot of `name`/`issue_number`/`api_detail_url`. Because issues — unlike the credit entities — have a local `cv_issue` table, the snapshot is redundant; the ref should just reference the issue row.
- **Change:** reduced `cv_volume_issue_ref` to `volume_id`, `ref_type`, `issue_id` (FK to `cv_issue`), and `key_order`, dropping the three snapshot columns (the updater drops them if an older table still has them). The server now resolves the display fields with `LEFT JOIN cv_issue ON i.id = r.issue_id`. The Node updater's backfill and `syncVolumes` upsert write only the id + key order.
- **Gotcha / follow-up:** the live API's first/last issue ids don't always resolve to a local `cv_issue` row (the DB is a synced subset — ~2.2% of refs are dangling). A `LEFT JOIN` keeps those refs, emitting the id with `null` display fields; this is the intended behavior for now (a dangling ref was previously fully denormalized). The Python updater is unaffected — it predates the join tables and still stores `first_issue`/`last_issue` as JSON.

### 2026-10-29 — Volume credits normalized into join tables (SRV-6c)

- **Context:** volume relationship data (the six `*_credits` arrays, `first_issue`, `last_issue`) was stored as denormalized JSON text on `cv_volume`; SRV-6 is normalizing these into join tables, staged per table with `cv_volume` first.
- **Change:** added `cv_volume_credit` (one row per credit entry: `volume_id`, `credit_type`, `position`, `credit_id`, `name`, `count`, `api_detail_url`, `site_detail_url`) and `cv_volume_issue_ref` (one row per first/last issue reference, with a `key_order` column recording the emitted key order). A `cv_volume.credits_presence` bitmask distinguishes an empty `[]` from a `null` collection, since the two serialize differently. The updater's `ensureVolumeCreditTables()` backfills the join tables from the JSON columns (id-ordered batches, idempotent) and drops the JSON columns; the server builds volume results from the join tables once the backfill marker (`credits_presence`) is present, and falls back to the JSON columns otherwise.
- **Gotcha / follow-up:** a key-shape audit of all 154k populated rows showed the credit entries have exactly one key shape (`id→name→count→api_detail_url→site_detail_url`, no `role`, no nulls), but `first_issue`/`last_issue` have **two** historical key-order variants with nullable `name`/`issue_number` — hence the `key_order` column. `team_credits` is always `[]`. Output was verified byte-for-byte identical on a copy of the live DB (41 detail responses + a list). The backfill runs automatically on the next `npm sync`; until then the server uses the JSON path and output is unchanged.

### 2026-10-29 — Node.js updater port (UPD-3)

- **Context:** the sync updater was Python (borrowed from Logical-Feedback-543 for use with comicrack), so running a sync required a Python environment separate from the zero-dependency Node server.
- **Change:** ported the updater to `src/updater.js` using `node:sqlite` and `fetch` (no npm dependencies), so sync and server share one runtime. Added `npm sync` / `npm sync:full`. The port preserves the field lists, the upsert SQL, the live API's retry contract (1.5s inter-call delay, 107 → 60s×attempt backoff, 100 → abort, 420 → 600s×attempt wait), the resume state, dated-database copy/cleanup, and the config-file/env key precedence. The Python `smtplib` email report and `tkinter` GUI picker have no zero-dependency Node equivalent and were dropped.
- **Gotcha / follow-up:** `node:sqlite` rejects boolean binds (Python's `sqlite3` coerces `True`/`False` to 1/0), so `jsonify` maps booleans to `1`/`0`; PRAGMAs must go through `exec()` rather than a prepared statement. The Python updater was removed from the repo when the Node port was adopted (UPD-5); its history is preserved in the git log.

### 2026-10-29 — Log levels and timestamps (SRV-10)

- **Context:** the JSON request/validation logs had no severity and no wall-clock time, so a busy log stream was hard to filter or correlate.
- **Change:** added a `log()` helper in `createApiServer` that stamps every entry with an ISO-8601 `timestamp` and a `level` (request logs are `info`; validation logs are `info` on a match, `warn` on a mismatch/missing/unavailable). `COMICVINE_LOG_LEVEL` (or the `logLevel` option) sets a minimum threshold that drops quieter entries, and the default logger now writes `warn`/`error` to stderr and the rest to stdout.
- **Gotcha / follow-up:** the level is resolved once at server construction, so a running server needs a restart to change `COMICVINE_LOG_LEVEL`.

### 2026-10-29 — Live-API validation on detail endpoints (SRV-8)

- **Context:** there was no way to confirm the bundled data still matched the live ComicVine API after a sync.
- **Change:** added `COMICVINE_VALIDATE=1` (or `validate: true`) so detail responses also diff the entity against the live API and report a `validation` field (`match`/`mismatch`/`missing_on_live`/`unavailable` + per-field diffs), and each diffed request logs a `type: "validation"` entry to stdout. The live key comes from `COMICVINE_API_KEY`. Extracted the per-resource field/relationship Sets into `src/fieldConfig.js` (shared by the server and the new `src/validate.js`) to avoid a require cycle; the live fetch is injectable for tests. Object references (e.g. a volume's `publisher`) diff by `id|name`, not a raw object.
- **Gotcha / follow-up:** validation only runs when a key is present, and issues are the only type whose collections are diffed (the live API returns collections only for issues — see UPD-1). It consumes live quota, so keep it off in normal service.

### 2026-10-29 — `/api/status` statistics endpoint (SRV-9)

- **Context:** there was no visibility into how stale or complete the local data was, or how the mock was being used.
- **Change:** added `/api/status` reporting per-table row counts, `cv_sync_metadata` last-sync dates, and per-endpoint request stats (counts, status codes, average duration) from an in-memory accumulator keyed by normalized endpoint path. Detail routes aggregate under `/api/{resource}/{id}/`; missing ids still count as HTTP 200 (the 101 envelope matches the live API).
- **Gotcha / follow-up:** stats reset on server restart; the endpoint is local-only and intentionally outside the ComicVine envelope.

### 2026-10-29 — Full sync, search-only forced limit, and rate-limit handling

- **Context:** the updater needed a one-time full refresh; search paging was being overridden by `COMICVINE_FORCED_LIMIT` on list endpoints too; and the live API's rate-limit response (`status_code: 107`) was aborting sync runs.
- **Change:** added `--full` to the updater; scoped `COMICVINE_FORCED_LIMIT` to the search endpoint only (`searchForcedLimit`); made `api_call` retry with escalating backoff on 107 and `validate_api_key` treat 107 as a valid-but-exhausted key.
- **Gotcha / follow-up:** the updater's Python/Node split is tracked as UPD-3 in `TODO.md`.

### Personal Notes and Observations

This project came into being because I was using Kapowarr and the comicvine api had an outage due to a recent php vulnerability that impacted many sites across the internet. Kapowarr uses the comicvine api to add new volumes and issues, so my local instance of Kapowarr was up but running with limited functionality. I noticed there were dumps of the comic vine db around the internet and thought well I can probably build an api using one of those. The first database I found turned out to be raw dumps of api calls, this version had basically the same data in the singular table and a copy of the plural table (so there was a cv_volume and cv_volumes table with the same data). This was probably a misunderstanding of the person doing the dump of the architecture (that the cv_volumes call was a way to list multiple volumes from the cv_volume table). I was able to get a working prototype up before service to the comicvine api was restored. Even after it was restored I decided that I had made enough progress to continue using the prototype. Initial versions of this api used that database until I realized that it was a raw dump of the api output. After this realization I rewired the api to use a more normalized database - still trying to clean up that mess but should have this resolved soon.

The bulk of this project used Visual Code/Github Copilot. I initially used the free plan tied to github until I burned through the tokens (this took about a day). I then rewired copilot to use LM Studio Bionic running Qwen 3.8 27B Splash running on a M5 Mac Studio with 64 GB of RAM, my developer workstation is a Windows 11/13th Gen Intel with 128 GB of RAM. This works pretty well if you dial down Reasoning to none (LM Studio/Qwen Splash doesn't support low). I found that basically in Agent mode it was best to ask copilot to add a todo item to implement a specific feature and then review it, and eventually ask copilot to implement it. Also copilot would kind of just go along with some foundational decisions like using the initial database with the raw dumps without any complaints. Integration with Kapowarr also required some human in the loop diagnosing and debugging but for the most part copilot/qwen performed well.

The updater for the normalized database was originally python code borrowed from Logical-Feedback-543 for use with comicrack. I've now migrated that code to node.js (the Python file was removed from the repo when the Node port was adopted) and am making modifications to the schema for the database that was used for that project.
