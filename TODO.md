- [x] **SRV-4 — Filters use `LIKE` partial matching for text fields.** *Cancelled (superseded by SRV-5):* single-value filters still use a case-insensitive substring match, but it is now backed by the FTS5 trigram index (with a LIKE fallback for short values / unindexed resources), so the semantics are unchanged and the open question is moot.
- [x] **SRV-5 — Use SQLite full-text search instead of `LIKE`.** Done: the updater creates a per-resource FTS5 trigram index (`cv_*_fts` on `name`/`aliases`/`deck`/`description`) and rebuilds it after each sync. The server detects the index and uses it for search (name) and single-value text filters via `ftsOrLike`, falling back to `LIKE '%value%'` for values under 3 characters or resources without an index — so the result set is unchanged but the common path is a fast token-based index scan.

- [x] **SRV-7 — Log to file.** Done: `COMICVINE_LOG_FILE` (or the `logFile` option) appends every emitted entry to a file in addition to the existing stdout/stderr logging. The file is size-rotated at `COMICVINE_LOG_MAX_SIZE` (default 10 MiB) into `<path>.1` … `<path>.<maxFiles>` generations (default 5), the oldest removed. Appends are synchronous (`fs.appendFileSync`) and best-effort — a filesystem error logs to stderr and skips the entry rather than crashing the server. Off by default. See the README "Developer Notes" entry.

- [x] **SRV-10 — Add log levels and timestamps.** Done: every log entry carries an ISO-8601 `timestamp` and a `level`; `COMICVINE_LOG_LEVEL`/`logLevel` sets a threshold, and the default logger routes `warn`/`error` to stderr.
- [ ] **SRV-11 — Relocate the updater to run inside the server process.** Run the Node updater ([src/updater.js](src/updater.js), from UPD-3) within the server rather than as a separate `npm sync` invocation, so a sync can be triggered from the running app (e.g. a `/api/sync` endpoint and/or a startup flag) instead of restarting. Design constraints to resolve first: (1) `createApiServer` opens the DB **read-only** (line 511) while the updater needs a **write/WAL** connection, so it must open its own connection (or the server needs a separate read-write handle); (2) the updater's `sleep` backoff/inter-call delays would **block the event loop**, so it must run off the main loop (worker thread or child process) or be restructured to non-blocking awaits; (3) the server's read connection is opened at startup, so it needs to observe the updater's committed writes (WAL reader visibility / re-open or fresh transaction after a sync). Decide the trigger mechanism, how sync status surfaces through `/api/status` (SRV-9), and how the read-only + write connections coexist.
- [x] **SRV-12 — Publisher blocklist on volume search.** Done: `COMICVINE_PUBLISHER_BLOCKLIST` (comma-separated ids) or the `publisherBlocklist` option on `createApiServer` (an array of ids) excludes a publisher's volumes from **both** the search and list endpoints via a `publisher_id NOT IN (...)` predicate (`publisherBlocklistPredicate` in [src/server.js](src/server.js)). It only affects volumes (the sole resource with a `publisher_id` column). On the list endpoint it is skipped when the request has an explicit `?filter=publisher_id=` / `?filter=publisher=` term, so a client can still query a blocked publisher directly; on search (no `?filter`) it always applies. Non-numeric tokens in the blocklist are ignored. See the README "Publisher blocklist" section.
- [x] **SRV-13 — API key authentication for incoming requests.** Done: `COMICVINE_API_KEYS` (comma-separated) or the `apiKeys` option on `createApiServer` enables optional key authentication. When one or more keys are configured, requests to the resource endpoints (search/list/detail) must present a matching key (via `extractApiKey`: `X-Api-Key`/`X_API_KEY` header → `Authorization: Bearer` → `api_key`/`key` query param); a missing or invalid key returns HTTP 401 with a ComicVine-style envelope (`{ error, status_code: 100 }`, matching the live API's "invalid API key" response). Authentication is **off by default** (empty list) so existing local usage is unchanged. The local-only `/api` index and `/api/status` endpoints stay open without a key, and the `OPTIONS` preflight allows the credential headers. See the README "Developer Notes" entry.
- [x] **SRV-14 — CORS support.** Done: the request handler computes the CORS headers once per request (`corsHeaders`) and stashes them on the response so every response path (JSON, XML, and JSONP) merges them in. `COMICVINE_CORS_ORIGINS` (comma/whitespace-separated) or the `corsOrigins` option on `createApiServer` is the allowlist. An **empty** allowlist is the default and means permissive `Access-Control-Allow-Origin: *` (the previous behavior, suitable for local dev). When origins are set, the request's `Origin` is echoed only on a match, with `Vary: Origin`; a non-matching `Origin` gets no grant. The `OPTIONS` preflight returns `204` with the origin grant plus `Access-Control-Allow-Methods: GET, OPTIONS` and `Access-Control-Allow-Headers: Content-Type, X-Api-Key, Authorization` (the SRV-13 credential headers). See the README "CORS" section and Developer Notes entry.
## Updater (`sqlite_cv_updater/sqlite_cv_updater.py`)

- [ ] **UPD-1 — Full sync does not refresh collections for non-issue types.** The live API returns collections (credits, relationships) only for issue resources, so a `--full` sync fully refreshes issues but leaves stored credits/relationships on volumes, people, teams, and story arcs at their last incremental values. Document or backfill these on a full pass.
- [x] **UPD-2 — Full sync is expensive (thousands of live calls).** Done: a `--full` sync is gated behind an explicit confirmation in [src/updater.js](src/updater.js). `confirmFullSync` prints a prominent warning (one unfiltered call per page across all six endpoints ≈ ~1.1M issue-detail calls; at the 200-calls/hour rate limit a full pass takes on the order of weeks and cannot be parallelized). In an interactive run it requires typing `yes`; in a non-interactive run it aborts unless `--yes`/`-y` is passed, so a stray `npm run sync:full` in cron cannot fire. The `--yes` flag is documented in the updater's help text and header.
- [x] **UPD-3 — Rewrite the updater in Node.js.** Port `sqlite_cv_updater/sqlite_cv_updater.py` to a Node.js script built on `node:sqlite` and `fetch`, so the sync tooling shares the server's runtime and drops the Python dependency.
- [ ] **UPD-4 — Issue/volume relationships can be invalid when the volume is absent.** The endpoints already run in the correct order (volumes before issues — see `runSync`), but each endpoint uses its own independent date window from its own `last_sync_date`, and a failed volume sync does not stop the issue sync. Two cases can leave an issue pointing at a volume that has no local row: (1) the volume sync exhausts its rate-limit retries and returns before upserting, while the issue sync later in the same run succeeds; (2) a newly-updated issue in the issue window references a volume whose update window the volume sync didn't cover and which has no prior row. Decide the remediation: validate the issue's `volume` reference against `cv_volume` and skip/null the relationship when the volume is absent (optionally re-syncing that specific volume on demand, or deferring the issue to a follow-up pass), so the DB never holds a dangling issue→volume reference.
