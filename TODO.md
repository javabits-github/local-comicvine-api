## Updater (`src/updater.js`)

- [ ] **UPD-1 — Full sync does not refresh collections for non-issue types.** The live API returns collections (credits, relationships) only for issue resources, so a `--full` sync fully refreshes issues but leaves stored credits/relationships on volumes, people, teams, and story arcs at their last incremental values. Document or backfill these on a full pass.
- [x] **UPD-2 — Full sync is expensive (thousands of live calls).** Done: a `--full` sync is gated behind an explicit confirmation in [src/updater.js](src/updater.js). `confirmFullSync` prints a prominent warning (one unfiltered call per page across all six endpoints ≈ ~1.1M issue-detail calls; at the 200-calls/hour rate limit a full pass takes on the order of weeks and cannot be parallelized). In an interactive run it requires typing `yes`; in a non-interactive run it aborts unless `--yes`/`-y` is passed, so a stray `npm run sync:full` in cron cannot fire. The `--yes` flag is documented in the updater's help text and header.
- [x] **UPD-3 — Rewrite the updater in Node.js.** Port `sqlite_cv_updater/sqlite_cv_updater.py` to a Node.js script built on `node:sqlite` and `fetch`, so the sync tooling shares the server's runtime and drops the Python dependency.
- [x] **UPD-4 — Issue/volume relationships can be invalid when the volume is absent.** Done: the endpoints already run in the correct order (volumes before issues — see `runSync`), but each endpoint uses its own independent date window from its own `last_sync_date`, and a failed volume sync does not stop the issue sync. Two cases can leave an issue pointing at a volume that has no local row: (1) the volume sync exhausts its rate-limit retries and returns before upserting, while the issue sync later in the same run succeeds; (2) a newly-updated issue in the issue window references a volume whose update window the volume sync didn't cover and which has no prior row. Fixed in [src/updater.js](src/updater.js): when an issue upsert fails with a `FOREIGN KEY` error (detected via `runWithFkDiagnostics`), the updater now checks whether the issue's referenced `volume_id` has a local `cv_volume` row; if it is missing, it queries the live ComicVine API for that specific volume (`volume/4000-${id}/`), upserts it via the shared `upsertVolume`, and retries the issue upsert once. If the volume cannot be fetched (rate-limit exhaustion / bad reference), the issue is skipped gracefully (no stats increment, no resume-state or metadata advance) rather than aborting the whole issue sync. `upsertVolume` and `upsertIssue` are extracted as reusable methods (the volume sync loop also uses `upsertVolume` with an identical SQL body). See UPD-6 for the FK diagnostics that surfaced these failures.
- [x] **UPD-5 — Retire the Python updater.** UPD-3 ported the updater to Node.js, but `sqlite_cv_updater/` (the original `sqlite_cv_updater.py` plus its README) was still in the repo. Removed the directory (its history is preserved in the git log) and updated the docs that referenced it ([README.md](README.md), [docs/architecture.md](docs/architecture.md), [.github/copilot-instructions.md](.github/copilot-instructions.md)) to point at `npm run sync` / [src/updater.js](src/updater.js) only.

## Raw API (`src/rawapi.js`)

- [x] **RAW-1 — A separate process to keep the rawapi database's verbatim JSON fresh.** Done: a new [src/rawapi.js](src/rawapi.js) + `npm run rawapi` / `npm run rawapi:full` — a third process, distinct from the server and the updater — keeps `comicvine_rawapi_*.db` (the 11 GB verbatim-JSON ground-truth snapshot from [docs/structure-validation-2026-11-10.md](docs/structure-validation-2026-11-10.md)) in step with the live API. All 11 `cv_*` tables share one uniform shape (`id`, `date_last_updated`, `site_detail_url`, `raw_api_response`); for every entity changed since the last sync, rawapi fetches the entity's **full detail object** and stores it **verbatim** (`JSON.stringify` of the API's `results` object) — the exact live-API shape, not the normalized columns [src/updater.js](src/updater.js) writes. Resources sync smallest-first so the largest table (`cv_issue`, ~1.1M rows) is always done **last**. Each resource runs the updater's two-phase pattern (a cheap `field_list=id` list call to collect the changed ids, then one detail call per id) with the updater's rate-limit/backoff and `cv_sync_metadata` resume tracking; a list call that still fails after all retries skips that table and the sync continues. The database is updated **in place** (no dated-copy mechanism); the default target is the most recent `comicvine_rawapi_*.db` in the cwd, overridable with `--db`. A full sync (~1.5M detail calls) is gated behind the same `--full`/`--yes` confirmation as the updater. The list endpoints' intermittent HTTP 401 / status 100 ("Invalid API Key") for a valid key — a transient rate-limit artifact — is retried with a 30 s backoff rather than treated as a hard failure. See the README "Raw API sync" section and the 2026-11-11 Developer Notes entry.
- [ ] **RAW-2 — Soft-delete: mark rows whose entity no longer exists on the live API (optional `--prune`).** The sync is upsert-only (`upsertRaw`, RAW-1), so an entity deleted on the live API leaves its row behind forever — the rawapi DB can only grow. Add an optional `--prune` pass that **marks** rather than removes: a new `deleted_at TEXT` column on the 11 uniform `cv_*` tables (NULL = alive; the sync timestamp when the entity is confirmed gone — one column serves as both flag and deletion timestamp, and the verbatim `raw_api_response` is preserved as the last known live shape). Detection: page the full list endpoint per resource (`field_list=id`, no date filter) to build the complete live id set, then `UPDATE … SET deleted_at = ?` for local rows whose id is absent; honors the UPD-12 `--resource` subset. Cost: during a `--full` run the marking is free (phase 1 already enumerates every live id); standalone `--prune` does only the list enumeration (no detail calls) but is still ~11k list calls for issues at the 200-calls/hour limit, so gate it behind the same `--yes` confirmation as the full sync. Safety: mark only when the enumeration completes fully (collected ids == `number_of_total_results`, zero failed pages — the known transient 401/status-100 must never read as mass deletion), plus a sanity floor (refuse to mark if the live count drops below, say, 50% of the local alive count). Self-healing: `upsertRaw` clears `deleted_at` when an entity is fetched alive again — but a false positive on an entity that never updates again persists until a full sync re-fetches it, which is why the guards above must be strict. Docs: the uniform shape gains a fifth column (README "Raw API sync" section). The updater (`localcv.db`) could get the same treatment, but the server would also need to filter soft-deleted rows from responses — a separate item.
